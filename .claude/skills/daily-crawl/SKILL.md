# daily-crawl — 日次クロール運用手順

仕様の正本は `docs/requirements-daily-crawl.md`。役割分担: **スクリプトが観測、Claudeが反映と検証**。

## 手順

1. `node crawler/daily.mjs` を実行し、stdoutのJSONレポートを読む(実行はネットワーク込みで2〜3分)
2. **watch差分の反映**:
   - `price_changed`: 該当 `properties/{id}.yaml` の `price_history` に追記。
     dateは `info_date`(媒体の情報提供日)、コメントにクロール日を記す。
     同日・同値の行が既にあれば追記しない(冪等)。反映後 `node engine/cli.js {id}` で再査定し、
     判定(保留⇄見送など)が変わったか確認する
   - `delisted_suspect`: YAMLに `delisted_observed: {date: クロール日, http: ステータス}` を追記。
     **成約とは断定しない**。7日以内に再掲載を確認したらこの項目を外す
   - `parse_error` / `fetch_error`: 台帳は触らず、報告にエラーとして含める
3. **discover差分**: レポートの `new` / `price_changed` を報告に列挙する(価格/地区/面積/築年/徒歩/URL)。
   報告前に `market/crawl/excluded.json` を確認し、既に除外判断済みの物件は「除外済み(理由)」として
   1行で触れるに留める(再提案しない)。
   **【ハザード判定は必ず複数媒体で行う】**(2026-08-12決定+同日の見落とし事故を反映):
   土砂災害警戒区域・**特別警戒区域(レッドゾーン)**・がけ条例・浸水想定・宅地造成工事規制区域に
   該当する物件は台帳に載せない。ただし **SUUMOの「その他制限事項」は該当物件でも空欄のことがある**
   (西が丘2の2棟現場は実際にSUUMOが空欄で、athomeの4業者掲載だけが特別警戒区域を明記していた)。
   そのため登録前には必ず:
     1. SUUMOの「その他制限事項」
     2. **athome掲載の「備考」欄(埋め込みJSONの `athomeBiko` に法令等制限が入る)**
   の両方を確認する。athome掲載が見つからない物件は「ハザード未検証」と明記して報告する。
   該当が判明したら excluded.json に理由・出典つきで追記する。
   **自動登録はしない**。ユーザーが登録を指示したら fudosan-appraisal スキルの登録フローを踏む。
   seen.json はスクリプトが更新済みなので、変更があればコミットに含める
4. **検証とデプロイ**(YAML変更があった場合のみ):
   `npm test` を実行し **exit codeを直接確認**(パイプで潰さない。落ちたらpushせず原因修正)→
   `node site/build.js` → 変更ページのSVG機械検査 → feature ブランチにコミット →
   main へ ff-merge → push → 本番URLをcurlで確認
5. **報告**: 値下げn件(物件名・幅・判定への影響)/ 新着n件 / 掲載終了疑いn件 / エラーn件。
   定期実行(Routine)ではこの要点を **PushNotificationツールで通知**する。
   すべてゼロの日は通知せず静かに終了してよい。**ただし月曜(JST)は変化ゼロでも1行の生存報告を通知する**

## 注意

- 探索媒体はSUUMO+athome(2026-08-12〜)。媒体横断の同一物件は指紋(地区丁目|価格|土地面積)で
  自動名寄せされるが、**媒体間の面積表記差(公簿/実測)があると指紋が外れて新着に重複が混ざる**。
  新着のうち台帳物件・既見物件と丁目+価格が一致するものは重複疑いとして扱い、新着として通知しない
- athomeの一覧から取れる徒歩分数はバス停等を拾って過小になることがある。登録時は詳細ページで駅徒歩を確認する

- 同一物件が別業者により別のnc番号で掲載されることがある(ncでは検知不能)。discoverの物件が
  台帳物件と重なって見える場合は、**詳細ページを取得して属性を突き合わせ、強一致なら台帳更新まで実施する**:
  - **強一致の基準(全て満たすこと)**: ①同一丁目 ②土地面積が完全一致(実測値の小数まで)
    ③建物面積が完全一致 ④間取りが一致。→ 同一物件と確定し、source_url未登録なら確認日と
    一致項目をコメントに記して登録、価格差があれば price_history に反映(date=媒体の情報提供日)
  - **一部一致(丁目+間取りのみ等)**: 同一開発の別棟・別区画の可能性があるため
    「重複掲載の疑い」として報告に留め、ユーザー確認を待つ
  - **【重要】価格の一致を同一物件の根拠にしてはいけない**(2026-08-12の取りこぼし事故)。
    新築の複数戸掲載は一覧が開発の代表価格(=最安戸の価格)を出すため、別戸どうしが同じ価格で
    表示される。逆に同一開発の別戸が同じ土地面積を持つこともある(西が丘2のC号棟/D号棟)。
    クローラは `sibling_hint` で以下を出し分けるので、**旗が立った新着は必ず掲載元の
    区画・住戸情報で戸を特定してから登録要否を判断する**(重複と即断しない):
      - `[別戸の可能性・要判断]` 価格一致・土地面積不一致 → **登録候補**。事故はこの型
      - `[別戸または価格改定・要判断]` 土地面積一致・価格不一致 → 区画情報で戸を特定
      - `[同一戸の疑い]` 価格・土地一致で建物面積のみ差 → 媒体の延床表記差(車庫算入等)。
        新規登録は不要な公算だが、台帳の面積表記を見直す価値はある
  - 突き合わせで台帳と媒体の記載が食い違う項目(私道負担・構造など)を見つけたら、
    査定入力を勝手に変えず、YAMLの該当noteに「表記不一致・要確認」として両論併記する
  - 前例: 2026-08-12 nishigaoka2-adcast-a(チラシ出所)を nc_21261057 と7項目一致で確定し、
    値下げ6980→6580を反映。私道負担の表記不一致(1.40/6.02m2)はnote記録に留めた
- クロールのリクエスト間隔・ページ上限はスクリプト側で制御済み。手動で連打しない
- 生HTMLやレポートJSONはリポジトリにコミットしない(コミット対象は properties/ と market/crawl/seen.json のみ)
