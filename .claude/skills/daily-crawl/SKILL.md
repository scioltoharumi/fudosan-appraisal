# daily-crawl — 日次クロール運用手順

仕様の正本は `docs/requirements-daily-crawl.md`。役割分担: **スクリプトが観測、Claudeが反映と検証**。

## 手順

1. `node crawler/daily.mjs` を実行し、stdoutのJSONレポートを読む(実行はネットワーク込みで2〜3分)
2. **watch差分の反映**:
   - `price_changed`: 該当 `properties/{id}.yaml` の `price_history` に追記。
     dateは `info_date`(媒体の情報提供日)、コメントにクロール日を記す。
     同日・同値の行が既にあれば追記しない(冪等)。反映後 `node engine/cli.js {id}` で再査定し、
     参照水準に対する位置(市場実勢中央値との差・上位四分位+交渉幅との差)がどう動いたか確認する。
     **買う/見送るの判定は出さない**(2026-08-13方針)
   - `delisted_suspect`: YAMLに `delisted_observed: {date: クロール日, http: ステータス}` を追記。
     **成約とは断定しない**。7日以内に再掲載を確認したらこの項目を外す
   - `parse_error` / `fetch_error`: 台帳は触らず、報告にエラーとして含める
3. **discover差分**: レポートの `new` / `price_changed` を報告に列挙する(価格/地区/面積/築年/徒歩/URL)。
   報告前に `market/crawl/excluded.json` を確認し、既に除外判断済みの物件は「除外済み(理由)」として
   1行で触れるに留める(再提案しない)。
   **【ハザード判定は必ず複数媒体で行う】**(2026-08-12決定+同日の見落とし事故を反映):
   土砂災害警戒区域・**特別警戒区域(レッドゾーン)**・がけ条例・浸水想定・宅地造成工事規制区域に
   該当する物件は台帳に載せない。ただし **SUUMOの「その他制限事項」は該当物件でも空欄のことがある**
   (西が丘2の2棟現場は実際にSUUMOが空欄で、athomeの4業者掲載だけが特別警戒区域を明記していた)。
   そのため登録前には必ず:
     1. SUUMOの「その他制限事項」
     2. **athome掲載の「備考」欄(埋め込みJSONの `athomeBiko` に法令等制限が入る)**
     3. **公式マップの機械照合**: `node crawler/geohazard.mjs "東京都北区<地区><丁目>丁目"`
        (国土地理院タイル。verdict が block なら掲載条件「台地側(荒川低地の浸水想定域外)」から外れる)
   の3つすべてを確認する。athome掲載が見つからない物件は「ハザード未検証」と明記して報告する。
   **②のathome掲載は「見つからなかった」で済ませない**(2026-08-13の監査で、新規4件すべて
   `athome: unchecked` としていたが実際には4件とも掲載が存在した)。探し方:
   北区の中古戸建一覧を**町名で絞った頁**から、価格・土地面積・建物面積・築年月の4点一致で特定する
   (`https://www.athome.co.jp/kodate/chuko/tokyo/kita-city/list/` の町名別リンクを辿る)。
   SUUMOと物件番号は無関係なので番号では引けない。
   **athomeにしか無い事実がある**: 実例として「私道通行料1,500円/月(私道持分無)」「接道 私道 位置指定有」
   「容積率の制限：前面道路制限有」「第2種高度地区」は、いずれもSUUMOには一切書かれておらず
   athomeの接道状況欄・備考欄・アピールポイントにのみ記載されていた。
   **掲載欄(1・2)には洪水浸水想定が原則載らない**(重要事項説明の義務項目であって広告欄の項目ではない)。
   2026-08-13に志茂1・志茂3が「suumo: none / athome: none」のまま台帳に残っていた事故の原因がこれ。
   逆に3は丁目代表点ベースなので崖線沿いの帯状区域を取りこぼす(西が丘2のレッドゾーン現場は
   代表点±400mの81点で0点)。**1・2と3は互いの穴を埋める関係なので、どれも省略しない**。
   新しい丁目の物件を登録したら `node crawler/hazard-grid.mjs` を回して market/hazard-grid.json を
   更新する(map.html の地区マーカーはこのJSONの代表点辞書を引くため、未登録の丁目は地図に出ない。
   その場合は map.html 冒頭に「代表点が未取得の地区」として警告が出る)。
   該当が判明したら excluded.json に理由・出典つきで追記する。
   **新着の自動登録(2026-08-13ユーザー指示・KO基準の正本は docs/requirements-daily-crawl.md §2.2)**:
   **KO判定はスクリプトが済ませてレポートに入れてくる**(`crawler/screen.mjs`)。手で詳細ページを
   取りに行かず、`event` と `ko` を見て処理を分ける:
     - `event: "new"`(ko.verdict=pass) → **そのまま自動登録する**。`ko.attrs` に土地/建物/間取り/
       築年月/徒歩/接道/用途地域/建ぺい容積/権利/情報提供日が入っているので、これを一次情報として
       YAMLを起こす(assumedの明示・source_urlの実在確認は従来どおり)。
       **`status` は `new`**(一覧で「新規」と表示され、人がまだ見ていないものを見分けられる)。
       `ko.caveat` があれば従い(SUUMO単独確認ならathome掲載も見る)、hazard_check欄に確認状況を残す
     - `event: "new_ko_blocked"` → 登録しない。報告に1行(物件・KOコード・理由)。
       スクリプトが seen.json に記録済みなので再提案は起きない。excluded.json への追記は
       **新しい現場を除外判断したときだけ**(既知現場の再掲は追記不要)。
       KOコードは KO1再建築不可 / KO2所有権以外 / KO3告知事項 / KO4重大ハザード / KO5必須項目不確定 /
       **KO6私道の通行料等の金銭負担**(2026-08-14追加)
     - `event: "new_ko_suspect"` → 除外済み現場の近接(`SITE_NEAR`)、丁目の縁がハザード(`AREA_EDGE`)、
       **私道持分なしの明記(`ROAD_NO_SHARE`)** のいずれか。登録も除外もせず、掲載元・公式マップ・
       私道の持分/通行料の確認が要る旨をユーザーに投げる
     - `event: "new_out_of_scope"` → 詳細ページの徒歩分が20分超・延床70m2以下・3室未満。報告のみ(対応不要)
     - `event: "ko_blocked_on_recheck"` → **既見だった掲載が値下げ時の再判定でKOになった**。登録しない。
       KOスクリーニング導入(2026-08-13)より前に初見だった掲載は諸元も ko 印も持たないため、
       値下げのたびに無審査で候補に上がっていた。再判定は3段で、**新着と同じ網を掛ける**:
       ①除外台帳の現場照合 ②丁目ハザード ③未審査(`ko_screened` なし)なら詳細ページまで取得してKOスキャン。
       ③を通ったものは `ko_screened` を立てて以後は取りに行かない。
       実例: 2026-08-21 西が丘2のレッドゾーン1号棟が別番号 nc_20593134 で再出現(①)/
       2026-08-22 志茂2の値下げ(②)・中里3の新築が**旧法賃借権**と判明(③)
     - `event: "out_of_scope_on_recheck"` → 既見の掲載が値下げ時の再判定で**掲載条件**を外れていた
       (延床70m2以下・3室未満・徒歩20分超)。報告のみ(対応不要)。
       2026-08-25: KOは通るが延床65.72m2の滝野川1が候補として上がった。KO(登録してはいけない)と
       掲載条件(探す気がない)は別物なので、再判定でも両方見る
     - `ko.verdict: "unknown"`(詳細未取得=予算切れ等) → 登録しない。翌日再判定される
   スクリプトが落とした件数は summary の ko_blocked / ko_suspects / out_of_scope に出る。
   通知には登録した物件の価格の位置(市場実勢中央値との差)と、落とした件数を含める。
   **買う/見送るの判定はしない**(2026-08-13方針。判断は人が行う)。
   seen.json はスクリプトが更新済みなので、変更があればコミットに含める
4. **検証とデプロイ**(YAML変更があった場合のみ):
   `npm test` を実行し **exit codeを直接確認**(パイプで潰さない。落ちたらpushせず原因修正)→
   `node site/build.js` → 変更ページのSVG機械検査 → feature ブランチにコミット →
   main へ ff-merge → push → 本番URLをcurlで確認
5. **報告**: 値下げn件(物件名・幅・市場実勢との差の変化)/ 新着n件 / 掲載終了疑いn件 / エラーn件。
   定期実行(Routine)ではこの要点を **PushNotificationツールで通知**する。
   すべてゼロの日は通知せず静かに終了してよい。**ただし月曜(JST)は変化ゼロでも1行の生存報告を通知する**

## 注意

- 探索媒体はSUUMO+athome(2026-08-12〜)。媒体横断の同一物件は指紋(地区丁目|価格|土地面積)で
  自動名寄せされるが、**媒体間の面積表記差(公簿/実測)があると指紋が外れて新着に重複が混ざる**。
  新着のうち台帳物件・既見物件と丁目+価格が一致するものは重複疑いとして扱い、新着として通知しない
- athomeの一覧から取れる徒歩分数はバス停等を拾って過小になることがある。登録時は詳細ページで駅徒歩を確認する

- 同一物件が別業者により別のnc番号で掲載されることがある(ncでは検知不能)。discoverの物件が
  台帳物件と重なって見える場合は、**詳細ページを取得して属性を突き合わせ、強一致なら台帳更新まで実施する**:
  - **強一致の基準(全て満たすこと)**: ①同一丁目 ②土地面積が完全一致(実測値の小数まで)
    ③建物面積が完全一致 ④間取りが一致。→ 同一物件と確定し、source_url未登録なら確認日と
    一致項目をコメントに記して登録、価格差があれば price_history に反映(date=媒体の情報提供日)
  - **一部一致(丁目+間取りのみ等)**: 同一開発の別棟・別区画の可能性があるため
    「重複掲載の疑い」として報告に留め、ユーザー確認を待つ
  - **【重要】価格の一致を同一物件の根拠にしてはいけない**(2026-08-12の取りこぼし事故)。
    新築の複数戸掲載は一覧が開発の代表価格(=最安戸の価格)を出すため、別戸どうしが同じ価格で
    表示される。逆に同一開発の別戸が同じ土地面積を持つこともある(西が丘2のC号棟/D号棟)。
    クローラは `sibling_hint` で以下を出し分けるので、**旗が立った新着は必ず掲載元の
    区画・住戸情報で戸を特定してから登録要否を判断する**(重複と即断しない):
      - `[別戸の可能性・要判断]` 価格一致・土地面積不一致 → **登録候補**。事故はこの型
      - `[別戸または価格改定・要判断]` 土地面積一致・価格不一致 → 区画情報で戸を特定
      - `[同一戸の疑い]` 価格・土地一致で建物面積のみ差 → 媒体の延床表記差(車庫算入等)。
        新規登録は不要な公算だが、台帳の面積表記を見直す価値はある
  - 突き合わせで台帳と媒体の記載が食い違う項目(私道負担・構造など)を見つけたら、
    査定入力を勝手に変えず、YAMLの該当noteに「表記不一致・要確認」として両論併記する
  - 前例: 2026-08-12 nishigaoka2-adcast-a(チラシ出所)を nc_21261057 と7項目一致で確定し、
    値下げ6980→6580を反映。私道負担の表記不一致(1.40/6.02m2)はnote記録に留めた
- クロールのリクエスト間隔・ページ上限はスクリプト側で制御済み。手動で連打しない
- 生HTMLやレポートJSONはリポジトリにコミットしない(コミット対象は properties/ と market/crawl/seen.json のみ)
