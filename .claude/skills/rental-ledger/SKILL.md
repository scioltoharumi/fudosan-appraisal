# rental-ledger — 戸建賃貸台帳の運用手順

購入台帳とは**別系統**。触るのは `rentals/` `engine/rent.js` `crawler/rent-*.mjs`
`market/rent-listings.csv` `site/templates/rent-*.js` だけで、`properties/` には手を入れない。

役割分担は購入版と同じ: **スクリプトが観測、Claudeが反映と検証**。

## 掲載条件(2026-08-18ユーザー決定)

| 項目 | 条件 | 種別 |
|---|---|---|
| 賃料+管理費 | 15〜25万円 | 圏外(out_of_scope) |
| 徒歩 | 最寄り駅10分以内・**路線は問わない** | 圏外 |
| 間取り | 3LDK以上(納戸Sは1室として数える。3DK・4Kは対象外) | 圏外 |
| 耐震 | 新耐震(1982年以降竣工。1981年竣工は判別不能なので落とさない) | 圏外 |
| 建物種別 | **一戸建てのみ**(テラス・タウンハウス=連棟は不可) | **KO(RKO3)** |
| 契約 | 普通借家、または**定期借家3年ちょうど**。定期借家の2年・4年以上はKO | **KO(RKO1)** |
| 告知事項 | あり=不可 | **KO(RKO2)** |
| エリア | 東京都北区 | — |
| ハザード | **マップ内も可**(除外しない。ただし必ず記録する) | — |
| トイレ2個 | **条件にしない**(下記) | — |
| 駐車場 | 不問 | — |

正本は `crawler/rent-screen.mjs` の `RENT_SCOPE` / `TEIKI_OK_YEARS` と `rentKoScreen()`。
tests/rent-screen.test.js が定数ごと固定しているので、条件を変えるときは
**テストとCLAUDE.mdの方針記述も同時に直す**。

### 定期借家を「3年ちょうど」だけ許容する理由(押し戻すこと)

2026-08-18ユーザー指示「三年のみOK(子供の小学校入学前タイミング)」。
**短いからKOではなく長さの要件**なので、2年(区切りに足りない)も4年以上(満了が入学後に来る)も
同じように落とす。「4年なら3年より長いから良いはず」と緩めないこと。
許容年数は `TEIKI_OK_YEARS`(クローラ側)と `engine/rent.js` の同名定数の**両方**に置いてあり、
tests/rent-engine.test.js が一致を検査する。片方だけ変えると落ちる。

定期借家を登録するときの注意:
- `terms.renewal_months: 0` を必ず入れる(期間満了で終了するので契約期間中の更新料は発生しない)
- 実質月額カーブの**契約期間より先は再契約前提の参考値**。再契約料の有無は掲載に出ないので
  モデルに入れていない。人に報告するときは満了時点(3年)の実質月額を使う
- 期日表記(「定期借家 西暦2030年3月まで」)は長さが読めないので `suspect`。入居日と満了日から実期間を確認する

### トイレ2個を条件にしない理由(押し戻すこと)

SUUMOの設備欄は**任意記載**で、北区の戸建賃貸54物件のうち「トイレ2ヶ所」の記載は12物件しかない。
条件に加えると候補が1件まで落ちる。**記載が無いことは「トイレが1つ」を意味しない**ので、
KOにも圏外にもせず事実欄(あり/記載なし)で持ち、内見・問い合わせで確認する。
YAMLでは `facilities.toilet2: true` または省略(= null = 不明)。**`false` は書かない**。

### ペット(猫)の扱い ── 落とすのは「不可の明記」だけ

ユーザーは**猫を飼っている**(2026-08-19)。ただしペットの記載も**任意記載**で、
母集団54物件のうち相談可18・不可の明記1・条件付き1・**記載なし34**。
台帳7件では相談可1・条件付き1・**記載なし5**なので、
**「記載なしも落とす」と台帳が7件→2件になる**。トイレ2個と同じ理由で掲載条件には入れない。

- 掲載条件で落とすのは `pet: "ng"`(不可の明記)**だけ**。`RENT_SCOPE.pet_require_documented` は
  false のまま。**変えるならユーザーに確認する**(方針変更=運用ルール0)
- 出所は**3箇所**あり、同じ掲載の中で食い違う: ①物件概要の「条件」欄 ②設備タグ ③備考の自由文。
  `petOf()` が4値に読み分ける: `ok` / `ng` / `cond`(不可の後ろに逃げ道=**人の判断へ**) / null
- **「ペット相談」は猫可を意味しない**(小型犬のみの掲載がある)。`pet_cat` が true のときだけ
  猫が名指しされている。**種別と頭数は必ず問い合わせで確認**し、結果を YAML に書く
- 追加費用は実質月額に効く。`terms.pet_monthly_man`(家賃上乗せ)/ `pet_shiki_months`(敷金増)/
  `pet_initial_man`(消臭等)。**掲載の自由文にしか出ないので人が書き写す**(機械抽出しない)。
  敷金は返還前提なので総額ではなく「入居時に用意する現金」にだけ乗る
- YAMLは `facilities.pet`(ok/cond/ng/null)・`pet_cat`・`pet_note`(原文の抜粋)

## 手順

1. `node crawler/rent-daily.mjs` を実行し、stdoutのJSONレポートを読む(2〜4分)
2. **watch差分の反映**:
   - `rent_changed`: `rentals/{id}.yaml` の `rent_history` に `{date, rent_man, kanri_man}` を追記(冪等)
   - `delisted_suspect`: `delisted_observed: {date, http}` を追記。**成約とは断定しない**。
     賃貸は回転が速く、掲載終了=申込が入った可能性が高いが、確認するまでは観測事実として書く
   - `contract_conflict`: **最優先で人へ報告**。台帳が普通借家としている物件が掲載で定期借家に
     変わっていたら、KO条件に触れるので登録の可否そのものが変わる
   - `parse_error` / `fetch_error`: 台帳は触らず、報告にエラーとして含める
3. **discover差分**:
   - `new`: 登録候補。下の「新規登録」へ
   - `new_ko_suspect`: **契約期間の記載が無い**ケースが主。落とさず人へ報告し、
     問い合わせで確定させるまで登録しないか、確定待ちと明記して登録する
   - `new_ko_blocked` / `new_out_of_scope`: 件数と理由を報告に**必ず出す**(黙って減らさない)
   - `gone_from_list`: 一覧から消えた既見物件。賃貸ではこれが主要な変化なので報告する
   - `new_undecided`: 詳細取得の予算切れ。翌日再判定されることを添えて報告する
4. **新規登録**(`rentals/{地区}{丁目}-{jncの数字部}.yaml`):
   - 詳細ページの実値を写す。**次の5欄を必ず開く**(2026-08-19の監査で、取りこぼしは全部この5欄で起きていた):
     `ほか初期費用` / `ほか諸費用` / `POINT` / `条件` / `入居`。
     鍵交換・消毒・防災グッズ・24時間サポート・更新料・退去時クリーニングはここにしか出ない。
     金額が読めるものを `terms.key_exchange_man` / `misc_initial_man` / `misc_monthly_man` /
     `cleaning_man` / `renewal_months` / `shikibiki_months` に入れる
     (原文は parseRentDetail が `misc_initial_raw` / `misc_other_raw` で拾うが、
      **万円への換算は人が行う**。自由文なので誤読の害が大きい)。
     鍵交換は「ほか初期費用」の合計に含まれることがあるので、既定2.2万との**二重計上に注意**
   - 公式ハザード照合を実行して `hazard_check.official` に記録:
     `node crawler/geohazard.mjs "東京都北区<地区><丁目>丁目"`。
     **除外はしないが記録は必須**。`家屋倒壊等氾濫想定区域(氾濫流)` が出たら浸水と別区分として明記する
   - 同一物件の別業者掲載は `duplicate_of: [jnc_...]` で名寄せする
     (賃料・専有面積・築年月・間取り詳細が一致すれば同一物件とみなしてよい)
   - `status: new` / `viewing: none` で登録。**メモは書かない**(運用ルール3)
5. **募集賃料プールの更新**: 新着が多い、または前回取得から日が空いたときは
   `node crawler/rent-pool.mjs` で `market/rent-listings.csv` を作り直す
   (一覧最大8頁+詳細100件超で約5分。**同時に2本走らせない**——相手サイトへの負荷になる)。
   **`RENT_CACHE_SAVE=/tmp/rentcache` を付けて取得HTMLを残すこと**。パーサを直したときに
   `RENT_CACHE_DIR=/tmp/rentcache` で再解析でき、相手サイトを叩き直さずに済む。
   出力の内訳(取得N掲載 → 一戸建てM掲載 → 名寄せ後P物件)と `⚠ 諸元が割れる物件` を必ず読む。
   プールが変わるとものさし比・探索の漏斗・回帰値が動くので、**再ビルドとテストを必ず通す**。
   CSVは**1物件1行**(同一物件の複数掲載は名寄せ済み・listing_count に元の掲載数)。
   **CSVを手で編集しない**——次の再生成で消える。直したいことがあればクローラ側の規則にする
6. **検証ゲート**: `npm test`(189件)と `node site/build.js` を**exit codeで**確認する(パイプで潰さない)
7. SVGを含むページを変えたときは見切れ検査:
   `npm i --no-save playwright-core && node tests/ui/cliff.svg.mjs site/dist/rent.html`
   (`rent-basis.html` も同様)。**縦軸ラベルに `rotate(-90)` を使わない**——回転前のbboxで判定されて落ちる
8. 一覧の列や保存まわりを変えたときは対話UI検査: `node tests/ui/rent.ui.mjs`(13項目)。
   **列を増やすと狭い画面でメモ欄が枠外へ出る**——これは実測でしか分からないので必ず通す
9. 反映は feature ブランチ → main へ ff-merge → push

## 報告の型

- 実質月額は**表示賃料と必ず並べる**(「表示21万 → 2年居住で25.1万/月」)。
  表示賃料だけを報告すると予算の判断を誤らせる
- ものさし比を出すときは**残差の幅**(site/dist/rent-basis.html の実数)を添える。
  台帳の物件間の比の差は、この標本ではおおむね誤差の内側
- **徒歩分の係数を根拠にしない**(判別不能・符号が「遠いほど高い」向き)
- 判定(借りるべき/見送るべき)は出さない(v3.0.0の思想)

## やってはいけないこと

- `properties/`(購入台帳)を触る
- メモ・交渉方針・個人的所感をYAMLやコミットに書く
- 掲載に無い数値を推測で埋める(仮定を使うなら `engine/rent.js` の既定値を使い、
  `evaluateRent().assumed` に名指しで出させる)
- `facilities.toilet2: false` と書く(記載が無いだけで、無いとは確認できていない)
- ハザード該当を理由に登録を見送る(**賃貸台帳はハザード内も対象**。記録して人に判断させる)
- 定期借家の許容年数を「3年以上」に緩める(3年ちょうどのみ。長さの要件であって下限ではない)
- `market/rent-listings.csv` を手で編集する(再生成で消える。規則はクローラ側に置く)
- サイトのテンプレートに実数を手書きする(プールを作り直すと同じページの中で矛盾する。
  数字は funnel / model / results から埋めること)
